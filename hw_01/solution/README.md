# Выбранная архитектура

## Облачное хранилище (Яндекс Диск)
Система позволяет загружать, хранить и работать с пользовательскими данными с возможностью совместного доступа к ним

Пользователи/акторы, которые работают с системой:
1. Пользователь, который загружает или работает с данными и управляет доступом к ним через выделенный интерфейс

## Ключевые сценарии
1. Загрузка, создание, редактирование файлов
2. Поиск и просмотр файлов
3. Скачивание файлов
4. Совместная работа и выдача прав доступа
5. Управление оплатой за услуги, управление тарифами - биллинг
6. Синхронизация данных с устройств (синхронная автозагрузка в реальном режиме времени или асинхронная)
7. Проверка антивирусом

## Масштаб работы
1. Миллионы пользователей - 20-25млн
2. Объем пользовательских данных - более 100 Петабайт
3. RPS - 100-200 тысяч

## 1. Компоненты

1 Интерфейс -> 2 CDN -> 3 Балансировщик -> 4 API Gateway -> 5 Сервисы (микросервисы) -> 6,7,8 БД

### 1.Клиентские интерфейсы: 
Веб-версия, мобильное приложение, десктопное приложение, REST API, приложение для ТВ
За что отвечает: Предоставление возможности пользователю работать с сервисами облачного хранилища

### 2.CDN 
За что отвечает: кеширование, доставка контента/данных с ближайших к пользователю серверов, используется для распределенных систем с большой нагрузкой

### 3. Балансировщик (Load Balancer)
За что отвечает: балансирует нагрузку, распределение трафика между серверами


### 4.API Gateway
За что отвечает: аутентификация, управление потоками данных и маршрутизация запросов между сервисами, агрегация ответов от сервисов, преобразования форматов (gprc в rest api)

### 5.Сервисы (микросервисы)

#### 5.1 Сервисы работы с файлами (просмотр, загрузка, создание, скачивание, редактирование, удаление)
1. Работа с файлами: 
- просмотр - view()
- загрузка - create()
- скачивание download() 
- редактирование edit()
- удаление - delete()
2. Уведомления
3. Запрос на доступ
4. Передача данных для аналитики
5. Передача данных для индексации (поиска)

#### 5.2 Сервис поиска
За что отвечает: быстрый поиск данных в хранилище

#### 5.3 Сервис управления доступом
За что отвечает: управление правами доступом к файлам

#### 5.4 Сервис безопасности проверки данных (антивирус)
За что отвечает: проверка безопасности загружаемых файлов

#### 5.5 Сервис оплаты (биллинг услуг)
За что отвечает: проведение оплаты и подписки на пользование услугами хранения данных

#### 5.6 Сервис уведомлений
За что отвечает: реагирование на события работы с файлом и передача нотификации клиенту

#### 5.7 Сервис аналитики
За что отвечает: получение событий и статусов над файлами для построения аналитики

#### 5.8 Сервис подписки
За что отвечает: управление данными подписок пользователей

#### 5.9 Сервис управления пользовательскими данными (профили пользователей)
За что отвечает: хранение пользовательских данных

### 6. База данных - Хранилище метаданных
За что отвечает: Структурированное хранилище данных для получения ссылок на файлы из объектного хранилища (поддержка шардирования и репликации)

### 7.База данных - Объектное хранилище данных
За что отвечает: Хранение больших файлов - байты файлов (картинки, видео, документы)

### 8. БД Аналитики (ClickHouse)

### 9. Локальные БД Микросервисов
- Локальная БД 5.5 Сервис биллинга PostgreSQL (поддержка шардирования и репликации)
- Локальная БД 5.3 Сервис управления доступом PostgreSQL (поддержка шардирования и репликации)
- Локальная БД 5.8 Сервис подписки (Subscription Service) PostgreSQL (поддержка шардирования и репликации)
- Локальная БД 5.9 Сервис профилей пользователей (User Service) (поддержка шардирования и репликации)
- REDIS для 5.9 Сервис профилей пользователей (User Service). REDIS для работы с кэш в условиях больших объемов данных

## 2. Потоки данных


### Поток данных 1
Пользователь хочет загрузить файл в облачное хранилище с проверкой доступа к возможности загрузки/созданию файла

1. Пользователь хочет начать загрузку файла, от внешнего интерфейса идет запрос от пользователя к **API Gateway**
2. **API Gateway** передает запрос на доступ к созданию файла пользователю к **5.3 Сервис управления доступом**
 - доступа нет - ошибка при создании
 - доступ есть, продолжение сценария (далее п.3)
3. **API Gateway** передает запрос на создание в **5.1 Сервис работы с файлами**
4. **5.1 Сервис работы с файлами** создает запись в **6. БД - Хранилище метаданных**, получает ссылку на размещение файла
5. **5.1 Сервис работы с файлами** передает обратно ссылку на создание через **API Gateway** к пользователю
6. Пользователь получает ссылку по которому можно загрузить файл в **7. БД - Объектное хранилище данных**
7. В случае неуспешной загрузки:
 - от внешнего интерфейса передается статус с ошибкой к **API Gateway** и далее повторно по сценарию
 - повторная попытка загрузить, запрос к **API Gatewayr**
8. В случае успешной загрузки:
 - от внешнего интерфейса передается успешный статус к **API Gateway**
 - от **API Gateway** передается статус в **5.1 Сервис работы с файлами**
9. По факту успешной загрузки **5.1 Сервис работы с файлами** передает данные о файле в **8. БД - Elasticsearch**

#### Поток данных 2
Пользователь хочет найти и просмотреть файл из облачного хранилища (проверка доступа за рамками процесса)

   1. Внешний интерфейс передает запрос на просмотр файла view() в **CDN**, если данные есть в кэше, то выдаются. если данных нет, то далее п.2
   2. Запрос от **CDN** к **API Gateway** за запросом файла
   3. **API Gateway** передает запрос на поиск в **5.2 Сервис поиска**
    - файл найден, в ответ передается ссылка на файл (далее п.4)
    - файл не найден - передается статус поиска в **API Gateway**, далее в **CDN** и во внешний интерфейс с ошибкой поиска
   4. **API Gateway** передает запрос на файл view() с ссылкой на файл к **5.1 Сервис работы с файлами**
   5. **5.1 Сервис работы с файлами** запрашивает данные на ссылку на файл из **6. БД - Хранилище метаданных**, возвращается ссылка на файл, далее передается в **API Gateway**, далее в **CDN** и во внешний интерфейс
   6. Данные кэшируются в **CDN** дл возможного использования
   7. Пользователь из внешнего интерфейса открывает ссылку и просматривает файл из **7. БД - Объектное хранилище данных**

#### Поток данных 3
Пользователь хочет оплатить подписку на облачное хранилище

1. **Внешний интерфейс** вызывает **API Gateway** для подключение новой подписки на месяц
2. **API Gateway** передает запрос на подключение подписки к **5.8 Сервис подписки**
3. 5.8 Сервис подписки проверяет тарифные планы, наличие актуальной подписки
    1. подписка уже оформлена - уведомление пользователю, что подписка уже активирована
    2. подписка не оформлена  - **5.8 Сервис подписки** запрашивает у **5.9 Сервис профилей пользователей** актуальность учетной записи и возможности оформить новую подписку - запрос от **5.9 Сервис профилей пользователей** к **5.5 Сервис биллинга**, формируется счет на оплату и ссылка для оплаты
4. **5.8 Сервис подписки** получает ссылку на оплату из **5.5 Сервис биллинга**
5. **5.8 Сервис подписки** передает ссылку на оплату в **API Gateway**
6. **API Gateway** передает ссылку на оплату в интерфейс. Пользователь переходит по ссылке и оплачивает во внешнем сервисе через платежный шлюз банка-клиента
7. Факт оплаты из **Платежного шлюза** передается в **5.5 Сервис биллинга** асинхронно
8. **5.5 Сервис биллинга** передает данные по факту оплаты в **5.8 Сервис подписки** асинхронно
9. **5.8 Сервис подписки** передает данные для уведомления клиента в **5.6 Сервис уведомлений**. **5.6 Сервис уведомлений** уведомляет клиента по sms/push/email
10. **5.5 Сервис биллинга** и **5.8 Сервис подписки** выгружают аналитику асинхронно в **5.7 Сервис аналитики**

## 4. Вопросы к авторам архитектуры
1. В основном решение построено на синхронных взаимодействиях, учтен ли риск и как организованы производительные мощности, чтобы клиент не долго ждал ответа при запросе, например, доступа к файлу? В каких процессах мы можем перейти на асинхронное взаимодействие?
2. При высокой нагрузке на Load Balancer/API Gateway при загрузке файлов или при ddos атаке, как должен быть организован процесс и взаимодействия?
3. При еще более высоком количестве пользователей или данных в БД Метаданных на PostgreSQL, какое решение требуется принять, чтобы сохранить работоспособность?
4. Как должен быть реализован процесс обхода блокировок работы Яндекс.Диск в других странах (или включен vpn)? Как должна вести себя система и что должен видеть пользователь?
5. Как должна быть организована безопасность персональных данных пользователей?
