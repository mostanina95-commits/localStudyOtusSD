# 8. Observability

- Мониторинг - это набор инструментов и сервисов, которые позволяют собирать, хранить, агрегировать и визуализировать метрики
- Алертинг - это набор инструментов, которые позволяют узнавать о каких-то важных изменениях в поведении системы (с помощью метрик)

Для мониторинга использовать open source решения - Prometheus (сбор и хранение метрик) + Grafana (визуализация и построение дашбордов)

### 8.1 Ключевые метрики (10-15)

Прорабатываются различные виды метрик, которые сопровождаются логированием состояний сервисов для дальнейшего разбора ошибок.
Структура лога:
- идентификатор запроса и трассировки (платеж, бронирование, и другое)
- время события timestamp
- связанные идентификаторы
- статус и описание ошибки для лучшего понимания что именно произошло
- источник лога: наименование и версия сервиса, в котором произошла ошибка

Виды метрик, которые рассматриваются:
- Инфраструктурные - состояние инфраструктуры: физические машины, сеть, системные сервисы: срu/disk/network
- Сервисные - состояние прикладных сервисов: описаны latency/rps
- Бизнес - состояние бизнес процессов и бизнес-сервисов

##### Инфраструктурные метрики
1. Загрузка CPU - состояние физических машин, сети и системных сервисов. Например, при загрузке более 90% вызывать алерт
2. Загрузка диска (Disk) - отслеживание нагрузки:
- заполнение памяти диска более 90% вызывать алерт
- количество операций в секунду, лимит - 70-80%
- задержа latency, больше 60мс - алерт
3. Трафик - отслеживание входящего и исходящего трафика
- отслеживание лимита входящего и исходящего трафика
- ошибки сети
- потери пакетов
- количество открытых соединений

##### Сервисные метрики SLI с указанием SLO
1. Доступность сервиса - в случае отсутствия ответа от сервиса при контрольных запросах для проверки доступности, вызывать алерт
2. API Gateway RPS	- количество запросов в секунду. Алерт (slo) - больше 2500-3000
3. Booking Service RPS	- количество запросов к сервису бронирования в секунду. Алерт - больше 500
4. Search Service RPS - количество запросов к сервису поиска в секунду. Алерт - больше 1000-2000
5. Payment Service RPS - количество запросов к сервису оплаты в секунду. Алерт - больше 200-300
6. Ticket Service RPS - количество запросов к сервису билетов в секунду. Алерт - больше 200-300
7. API Gateway latency (задержка) - алерт больше 200мс
8. Search latency (задержка) - время отклика сервиса поиска, алерт больше 300мс
9. Booking latency (задержка) - время отклика сервиса бронирования, алерт больше 1000мс
10. Payment latency (задержка) - время отклика сервиса оплаты, алерт больше 1000мс

##### Бизнес-метрики
1. DAU - количество активных пользователей за день. Алерт, если меньше среднего значения - меньше 2млн
2. Количество просмотров мероприятия в день
3. количество совершенных поисков в день (обращение к сервису поиска), время поиска (выдача результата из сервиса поиска)
4. Статусы бронирования за день/ час - количество оплаченных, не оплаченных в ожидании/ в ошибке/ истекших по времени оплаты 
6. Статусы оплат за день - количество успешных, ошибок оплат, возвратов, выручка за день
7. Статусы билетов - среднее время генерации билета, ошибок при генерации, успешных
8. Статусы регистраций в день - успешные, время сессии



### 8.2 Алерты (5-7)
https://github.com/mostanina95-commits/localStudyOtusSD/blob/hw2/hw_05/%D0%A8%D0%B0%D0%B1%D0%BB%D0%BE%D0%BD%20%D0%BE%D0%BF%D0%B8%D1%81%D0%B0%D0%BD%D0%B8%D1%8F%20%D0%B0%D0%BB%D0%B5%D1%80%D1%82%D0%BE%D0%B2.md

В случае превышения верхней границы метрик, должен быть отправлен алерт в систему мониторинга и отображен на дашбордах Grafana. Каждый алерт должен быть доступен для понимания и иметь конкретные шаги исправления ошибок техподдержкой

Реализовать следующие виды алертов:
##### 1. Критические алерты с превышением метрик в 10-15 раз
- недоступность одного из сервисов, в том числе внешнего (например платежного шлюза)
- исчерпание дискового пространства и превышение показателей инфраструктурных ресурсов срu/disk/network
- превышение задержки ответа от одного из сервисов

##### 2. Предупреждения
- приближение к лимитам инфраструктурных ресурсов срu/disk/network 
- рост времени ответов от сервисов (latency)
- рост ошибок 4ХХ от сервисов (например, при создании бронирования, оплате, генерации билетов, и другие)
- приближающийся срок окончания действия сертификатов


**Пример**, критичный алерт по превышению ответа одного из сервисов:
- Название:   "p95 latency booking-service выше SLO"
- Условие/порог: p95 > 1000мс в течении 5 минут
- Severity:   critical
- Что означает: Сервис бронирования отвечает с запозданием, возможно повышенное ожидание со стороны пользователей, что повлечет отток клиентов от системы и недополучение выручки
- Вероятная причина: Насыщение пула запросов к сервису, повышенная нагрузка на трафик
- Реакция (runbook): Проверить инфраструктурные метрики (трафик, загрузку диска, ошибки сети)
