## Выбранная система
Система Доставка еды "Яндекс Еда" с количеством пользователей более 20 млн в 400+ городах
Система позволяет заказывать еду из магазинов и ресторанов.
Ключевые сложности - Геолокация, real-time статусы, пиковые нагрузки

#### Объектная модель
1. Пользователь - клиент (User)
2. Курьер (Courier)
3. Заказ (Order)
4. Корзина (Cart)
5. Локация / Местоположение (Location)
6. Стоимость заказа (Order cost)

#### Бизнес-требования (основные бизнес процессы и сценарии)
1. Клиент ищет доступные магазины и рестораны с учетом своего адреса (геолокация)
2. Клиент создает заказ на доставку из доступного магазина или ресторана с поиском нужных товаров
3. Сбор товаров/продуктов в корзину в магазине или ресторане
4. Расчет стоимости корзины с учетом доставки
5. Оплата заказа
6. Назначение курьера на доставку
7. Отслеживание статуса заказа (создание, оплачено, принято к исполнению магазином или рестораном, принято курьером к доставке, отменено)
8. Уведомление пользователей (клиента/ курьера/ рестораны или магазины) о статусах заказа

#### Ограничения, которые не учитываются в архитектурном решении
1. Внешние системы и сервисы, которые интегрируются с системой Доставки - платежный шлюз и кассы, система геолокации и карт, система уведомлений, системы и личные кабинеты магазинов/ресторанов
2. Добавление мест по пути, цветы
3. Рекламные кампании
4. Саппорт и техподдержка
5. Процесс сбора отзывов
6. Процесс бронирования в ресторанах
7. Процесс самовывоза

#### Нефункциональные требования
1. **Время отклика (latency)** на поиск ресторана или магазина (меньше 200 мс), оформление заказа (1-2 секунды), обновление геопозиции курьера (меньше 1 секунды), поиск товара из каталога (меньше 200 мс)
2. **Общая пропускная способность (throughput)**, а также в пиковые нагрузки (обед, ужин) - примерно 10 000 - 100 000+ RPS. Для каждого процесса (поиск магазина/ресторана, оформление заказа, поиск и трекинг курьера, оплата, аналитика, и др.) RPS различается
3. **Масштабируемость (Scalability)** в случае роста количества пользователей, а также магазинов и ресторанов - вертикальная (увеличение мощности и показателей серверов) и горизонтальная (увеличение количества серверов). Масштабирование может быть достигнуто при помощи шардирования (разбиение и хранение данных на разных серверах в случае увеличенного количества данных) и балансировщика между шардами
4. **Доступность (SLA)** - целевое 99,9%
5. **Отказоустойчивость** - падение одного из сервисов система Доставки не должно останавливать процессы работы над заказом и потерю данных. Требуется обеспечить сохранение данных при помощи репликации
6. **Безопасность** - шифрование, аутентификация и авторизация
7. **Надежность данных** - гарантированная доставка событий (например в процессе оплаты и подтверждения заказа - оплата совершилась, заказ должен быть принят) и индепотентность (при нажатии кнопки создать заказ - должен быть создан только один заказ без дублирования)
8. **Логирование и метрики** - хранение логов для аудита, а также сбор технических и бизнес-метрик для дальнейшего анализа
9. **Гео-распределенность** и маршрутизация пользователей на ближайшие дата-центры - использование CDN для снижения задержек и кэширования
10. **Обратная совместимость** взаимодействия сервисов и поддержка версионности системного API, а также интеграций с внешними системами


## 1. Декомпозиция
Используемые сервисы:

### 1.Пользовательские интерфейсы: 
#### 1.1 Пользователь - клиент (User)
Интерфейс (Веб-версия, мобильное приложение, десктопное приложение), который должен предоставлять клиентам-пользователям услугу - возможность заказа доставки еды из магазинов или ресторанов

#### 1.2 Курьер (Courier)
Интерфейс (Веб-версия, мобильное приложение) для курьера, который должен предоставлять курьеру возможность работать с заказом

### 2.CDN 
Кеширование, доставка контента/данных с ближайших к пользователю серверов, используется для маршрутизации пользователя на ближайшие дата-центры с целью снижения задержек работы системы

### 3. Балансировщик (Load Balancer)
Басансирование нагрузки, распределение трафика между серверами


### 4.API Gateway
Единая точка для всех запросов:
Аутентификация и авторизация, управление потоками данных и маршрутизация запросов между сервисами, агрегация ответов от сервисов, преобразования форматов (например gprc в rest api)

### 5.Сервисы (микросервисы)

#### 5.1 Сервис процессинга заказов (Order Service processing)
Основной сервис работы с заказами и его жизненным циклом и статусами:
Отслеживание статуса заказа (создание, оплачено, принято к исполнению магазином или рестораном, принято курьером к доставке, отменено).
Сервис-оркестратор координирует другие сервисы

#### 5.2 Сервис корзины (Cart Service)
Управление корзиной с товарами клиента:
Добавление, изменение или удалений позиций корзины, просмотр и расчет стоимости корзины, синхронизация и проверка наличия товаров у партнеров (ресторан/магазин)

#### 5.3 Сервис управления пользовательскими данными (User Profile Service)
Управление данных профилей пользователей - клиентов и курьеров для целей аутентификации/авторизации, поиска ближайших магазинов/ресторанов, получения данных для заказа

#### 5.4 Сервис поиска (Search Service)
Поиск доступных: товаров, магазинов/ресторанов в системе Доставки

#### 5.5 Сервис оплаты (Payment Service)
Обработка платежей и управление стоимостью товаров, интеграция с внешними платёжными шлюзами, управление финансовыми транзакциями

#### 5.6 Сервис уведомлений (Push/notification Service)
Отправка уведомлений пользователям - клиентам/ курьерам/ ресторанам и магазинам

#### 5.7 Сервис аналитики (Analytics Service)


#### 5.8 Сервис геолокации (Location Service)

#### 5.9 Сервис работы с партнерами (Restaurant/Partner Service)
