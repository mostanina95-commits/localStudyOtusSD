Требуется обеспечить надежность системы от сбоев/ отказов и остановок системы средствами репликации, бэкапирования и разнесения данных на другие регионы

Термины:
- High Availability (HA) - Высокая доступность (99.9%+)
- RTO	Recovery Time Objective - за какое время обязаны восстановиться
- RPO	Recovery Point Objective - сколько данных допустимо потерять
- Failover - Переключение на резерв
- Failback - Возврат на основной узел
- Standby	- Резервный узел
- PITR - Point-in-Time Recovery (восстановление на момент)
- DR - Disaster Recovery
- Failover Region	- Регион для переключения

### 6.1 RTO/RPO по сервисам, схемы репликации
- Синхронная репликация - ожидание подтверждения коммита и записи на N реплик или большинство реплик (RPO=0). Риск: задержки при записи в реплики
- Асинхронная репликация - нет ожидания подтверждения коммита, реплика догоняет изменения, минимальная задержка на клиенте (RPO>0). Риск: могут быть потеряны данные при переключении на резервный узер
- Полусинхронная репликация - ожидание подтверждения хотя бы одной реплики, компромиссное решение

Решение репликации:
Выполняется репликация для критичных баз данных сервиса мероприятий: PostgreSQL (бронирования, билеты, платежи, пользователи, авторизация, уведомления, мероприятия, аналитики)

#### Паттерны отказоустойчивости (circuit breaker, retry, timeout, bulkhead)
В решении используются следующие паттерны:
1. **Circuit Breaker** (остановка запросов к сервису). Например:
- при оплате клиентом, когда сервис оплаты обращается к внешнему платежному сервису. Платежный сервис не отвечает - осуществляется остановка запросов. Такой подход останавливает поток ошибок и снижает нагрузку
- при генерации билетов, когда сервис бронирования передает запросы на создание билетов, а сервис билетов не отвечает и упал в ошибку
2. **Retry** (Повторные попытки запросов к сервису через определенный промежуток времени), учитывается только для идемпотентных операций (GET)
- при авторизации, когда устанавливается определенное количество попыток при авторизации, например 3-5 раз сервис пытается авторизовать пользователя 
- при оплате - 3-5 попыток при обращении к внешнему сервису
3. **Timeout** (Таймаут - установка времени ожидания, в течении которого сервис может ответить). Например:
- пользователь ждет вход в систему до 30 секунд
- бронирование производится за 10-20 секунд
- билет генерируется за 20-30 секунд
- оплата с взаимодействием внешнего платежного сервиса за 10-15 секунл
4. **Bulkhead** (ограничение количества параллельных запросов к сервисам). Распределение ограничений параллельных потоков по сервисам в системе. Например, каждый сервис поддерживает по 30-40 потоков, что не блокирует работу все сервисов, если один из них упал


### 6.2 План DR (Disaster Recovery)
1. Выполнение асинхронной или полусинхронной репликации данных между регионами
2. Обнаружен сбой в регионе, сервис недоступен
3. Зафиксирован сбой, поступил алерт об ошибке, техподдержка подтвердила и установила сбой
4. Переключение DNS на другой DR-регион. Сервисы-реплики становятся основными
5. Производится проверка сервисов
6. Уведомление пользователям о доступности системы (работает запасной DR-регион)
7. Когда основной регион восстановлен - производится обратный переход с реплики
