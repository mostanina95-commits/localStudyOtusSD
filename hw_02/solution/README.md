## Выбранная система
Система Доставка еды "Яндекс Еда" с количеством пользователей более 20 млн в 400+ городах
Система позволяет заказывать еду из магазинов и ресторанов.
Ключевые сложности - Геолокация, real-time статусы, пиковые нагрузки

#### Объектная модель
1. Пользователь - клиент (User) - заказчик 
2. Курьер (Courier)
3. Заказ (Order) - по окончанию сбора корзины создается заказ с рассчитанной стоимостью доставки
4. Корзина (Cart) - агрегирующая сущность товаров
5. Локация / Местоположение (Location)
6. Стоимость заказа (Order cost)

#### Бизнес-требования (основные бизнес процессы и сценарии)
1. Клиент ищет доступные магазины и рестораны с учетом своего адреса (геолокация). Клиент создает заказ на доставку из доступного магазина или ресторана с поиском нужных товаров
2. Сбор товаров/продуктов в корзину в магазине или ресторане
3. Расчет стоимости корзины с учетом доставки
4. Оплата заказа
5. Назначение курьера на доставку
6. Отслеживание статуса заказа (создание, оплачено, принято к исполнению магазином или рестораном, принято курьером к доставке, отменено)
7. Уведомление пользователей (клиента/ курьера/ рестораны или магазины) о статусах заказа

#### Ограничения, которые не учитываются в архитектурном решении
1. Внешние системы и сервисы, которые интегрируются с системой Доставки - платежный шлюз и кассы, система геолокации и карт, система уведомлений, системы и личные кабинеты магазинов/ресторанов
2. Добавление мест по пути, цветы
3. Рекламные кампании
4. Саппорт и техподдержка
5. Процесс сбора отзывов
6. Процесс бронирования в ресторанах
7. Процесс самовывоза

#### Нефункциональные требования
1. **Время отклика (latency)** на поиск ресторана или магазина (меньше 200 мс), оформление заказа (1-2 секунды), обновление геопозиции курьера (меньше 1 секунды), поиск товара из каталога (меньше 200 мс)
2. **Общая пропускная способность (throughput)**, а также в пиковые нагрузки (обед, ужин) - примерно 10 000 - 100 000+ RPS. Для каждого процесса (поиск магазина/ресторана, оформление заказа, поиск и трекинг курьера, оплата, аналитика, и др.) RPS различается
3. **Масштабируемость (Scalability)** в случае роста количества пользователей, а также магазинов и ресторанов - вертикальная (увеличение мощности и показателей серверов) и горизонтальная (увеличение количества серверов). Масштабирование может быть достигнуто при помощи шардирования (разбиение и хранение данных на разных серверах в случае увеличенного количества данных) и балансировщика между шардами
4. **Доступность (SLA)** - целевое 99,9%
5. **Отказоустойчивость** - падение одного из сервисов система Доставки не должно останавливать процессы работы над заказом и потерю данных. Требуется обеспечить сохранение данных при помощи репликации
6. **Безопасность** - шифрование, аутентификация и авторизация
7. **Надежность данных** - гарантированная доставка событий (например в процессе оплаты и подтверждения заказа - оплата совершилась, заказ должен быть принят) и индепотентность (при нажатии кнопки создать заказ - должен быть создан только один заказ без дублирования)
8. **Логирование и метрики** - хранение логов для аудита, а также сбор технических и бизнес-метрик для дальнейшего анализа
9. **Гео-распределенность** и маршрутизация пользователей на ближайшие дата-центры - использование CDN для снижения задержек и кэширования
10. **Обратная совместимость** взаимодействия сервисов и поддержка версионности системного API, а также интеграций с внешними системами


## 1. Декомпозиция

### 1. Пользовательские интерфейсы (actor) 
#### 1.1 Пользователь - клиент (User)
Интерфейс (Веб-версия, мобильное приложение, десктопное приложение), который должен предоставлять клиентам-пользователям услугу - возможность заказа доставки еды из магазинов или ресторанов

#### 1.1 Курьер (Courier)
Интерфейс (Веб-версия, мобильное приложение) для курьера, который должен предоставлять курьеру возможность работать с заказом

### 2 Инфраструктура
### 2.1 CDN
Кеширование, доставка контента/данных с ближайших к пользователю серверов, используется для маршрутизации пользователя на ближайшие дата-центры с целью снижения задержек работы системы

### 2.2 Балансировщик (Load Balancer)
Басансирование нагрузки, распределение трафика между серверами


### 3. Сервисы

### 3.1 API Gateway - stateless
Единая точка для всех запросов:
Аутентификация и авторизация, управление потоками данных и маршрутизация запросов между сервисами, агрегация ответов от сервисов, преобразования форматов (например gprc в rest api)

#### 3.2 Сервис заказов (Order Service) - stateless
Основной снхронный сервис работы с заказами и его жизненным циклом и статусами:
Отслеживание статуса заказа (создание, оплачено, принято к исполнению магазином или рестораном, принято курьером к доставке, отменено).
Сервис-оркестратор, координирует другие сервисы

#### 3.3 Сервис процессинга заказов (Order Service processing) - stateless
Асинхронный сервис обработки статусами заказов, который работает через брокер сообщений, получая и распространяя события над заказом

#### 3.4 Сервис корзины (Cart Service) - stateless
Управление корзиной с товарами клиента:
Добавление, изменение или удалений позиций корзины, просмотр и расчет стоимости корзины, синхронизация и проверка наличия товаров у партнеров (ресторан/магазин)

#### 3.5 Сервис управления пользовательскими данными (User Profile Service) - stateless
Управление данных профилей пользователей - клиентов и курьеров для целей аутентификации/авторизации, поиска ближайших магазинов/ресторанов, получения данных для заказа

#### 3.6 Сервис поиска (Search Service) - stateless
Поиск доступных: товаров, магазинов/ресторанов в системе Доставки

#### 3.7 Сервис оплаты (Payment Service) - stateless
Обработка платежей и управление стоимостью товаров, интеграция с внешними платёжными шлюзами, управление финансовыми транзакциями

#### 3.8 Сервис уведомлений (Push/notification Service) - stateless
Отправка уведомлений пользователям - клиентам/ курьерам/ ресторанам и магазинам

#### 3.9 Сервис аналитики (Analytics Service) - stateless
Обработка поступающих данных от сервисов для возможности аналитики и логирования. Сервис взаимодействует с ClickHouse для передачи данных с последующим хранением и построением дашбордов

#### 3.10 Сервис геолокации (Location Service) - stateless
Сервис работы с адресами и картами

#### 3.11 Сервис работы с партнерами (Partner Service) - stateless
Сервис, взаимодействующий с внешними системами ресторанов и магазинов. Сервис получает и передает данные по позициям товаров 

#### 3.12 Сервис работы с курьерами (Courier Service) - stateless
Управление данными курьерами - статусами назначения и доставки заказов, геолокацией и адресами доставки


#### 3.13 ClickHouse - stateful
Аналитическая витрина, получает данные через Kafka из БД Order Service

### 3.14 ElasticSearch - stateful
Сервис для полнотекстового поиска данных товаров, продуктов

### 4. Локальные БД Микросервисов - stateful
- БД, REDIS Сервис заказов (Order Service)
- БД, REDIS Сервис корзины (Cart Service)
- БД, REDIS Сервис управления пользовательскими данными (User Profile Service)
- БД Сервис оплаты (Payment Service)
- БД Сервис уведомлений (Push/notification Service)
- БД, REDIS Сервис геолокации (Location Service)
- БД, REDIS Сервис работы с партнерами (Restaurant/Partner Service)
- БД, REDIS Сервис работы с курьерами (Courier Service)




### 10. Внешние системы
- Провайдер уведомлений - Внешняя система, которая отправляет уведомления пользователям системы
- Платежная система - Внешний платежный шлюз
- Система ресторанов и магазинов - Внешние системы ресторанов и магазинов, которые выставляют товары для доставки или бронирования
- Система геолокации (Яндекс карты) - Внешняя система работы с геолокацией и картами, которая позволяет системе доставки отслеживать в реальном времени зоны доставки и доступные магазины/ рестораны для клиента, время доставки и др.

## 3. Протоколы и взаимодействия между сервисами
- REST API (HTTP/1.1, HTTP/2) - взаимодействие с клиентскими интерфейсами (web/mobile), с интерфейсами внешних систем публичных API
- gRPC (HTTP/2)- внутрисистемное взаимодействие для сервисов для поддержки масштабирования системы и высокой нагрузки
- Message broker (Kafka) - Применяется в сборе аналитики (Сервис аналитики (Analytics Service)), при передаче уведомлений (Сервис уведомлений (Push/notification Service)) и рассылок клиентам
- WebSocket/ SSE - взаимодействие с (web/mobile)

#### 1. Внутритервисное взаимодействие Сервиса заказов и Сервиса процессинга заказов
Сервис заказов фиксирует и передает асинхронно произошедшее событие в сервис процессинга заказов через брокер Kafka. Сервис процессинга должен в ответ отправить статус загрузки события через статусный топик. Отслеживание статусов потребуется для последующей аналитики

#### 2. Сервис заказов (Order Service) -> Сервис оплаты (Payment Service)
Сервис заказов синхронно через REST API/ gRPC вызывает сервис оплаты для создания/ подтверждения/ получения статуса оплаты. Сервис заказов дожидается ответа от сервиса оплаты для подтверждения операции и статуса оплаты. Потребитель операции оплаты - клиент (веб/ мобильное приложение). Средний отклик - 1,5–2 секунды, чтобы клиент не покинул страницу, а при пиковых нагрузках допустимы несколько секунд, но не больше 5–15 секунд


#### 3. Сервис процессинга заказов (Order Service processing) -> Сервис уведомлений (Push/notification Service)
Асинхронное взаимодействие между сервисами, Сервис процессинга заказов передает фактические произошедшие события для уведомления клиента через gRPC protobuf. Далее - потребитель уведомления клиент или курьер


#### 4. Сервис заказов (Order Service) -> Сервис корзины (Cart Service)
Сервис заказов передает синхронные запросы к сервисе корзины для создания/ изменения/ и других запросов для получения статуса корзины. Средний отклик - 1,5–2 секунды, чтобы клиент получил актуальный статус корзины, а при пиковых нагрузках допустимы несколько секунд, но не больше 5–15 секунд


## 4. API-контракты


#### Методы для работы с партнерами (ресторанами/магазинами)
User -> CDN -> API GW -> Сервис работы с партнерами (Restaurant/Partner Service)

- GET /api/v1.0/partner{id} - Получение информации о ресторане/магазине
- GET /api/v1.0/partner/item/{id} - Запрос данных товара
  
____
#### Методы для работы с корзиной (заказ на доставку)
User -> CDN -> API GW -> Сервис процессинга заказов (Order Service processing) -> Сервис корзины (Cart Service) -> Сервис работы с партнерами (Restaurant/Partner Service)

- POST /api/v1.0/cart/create - создание корзины 
- POST /api/v1.0/cart/addIitem - добавление позиции в корзине (товар или позиция в ресторане)
- GET /api/v1.0/cart/{id} - получение статуса корзины
- GET /api/v1.0/cart/item{id} - получение данных товара из корзины
- PUT /api/v1.0/cart/update{id} - обновление данных корзины
- PUT /api/v1.0/cart/delete{id} - удаление позиции из корзины

____
#### Методы для работы с заказом на доставку
User -> CDN -> API GW -> Сервис процессинга заказов (Order Service processing) -> Сервис корзины (Cart Service) -> Сервис работы с партнерами (Restaurant/Partner Service)

- POST /api/v1.0/order/create - создание заказа. Ответ - id заказа
- POST /api/v1.0/order/addcart{id} - добавление корзины с id в заказ
- GET /api/v1.0/order{id} - получение статуса заказа. Ответ - статус, согласно статусной модели
- PUT /api/v1.0/order/update{id} - обновление данных заказа с id
- PUT /api/v1.0/order/delete{id} - удаление заказа
____


#### Методы для работы с оплатой заказа
- POST /api/v1.0/payment/create - Создание платежа
- POST /api/v1.0/payment/approve - Авторизация платежа (подтверждение ранее захолдированной суммы)
- POST /api/v1.0/payment/refund - Возврат платежа (возврат суммы авторизованного платежа)
- POST /api/v1.0/payment/reverse - Отмена авторизации
- POST /api/v1.0/payment/purchase - Подтверждение платежа
- GET /api/v1.0/paymentinfo{paymentId} - Получение информации о платеже
